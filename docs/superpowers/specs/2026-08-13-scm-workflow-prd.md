# SCM 발주·입고관리 시스템 PRD

## 1. 문서 개요

### 1.1 목적

본 문서는 기기·옵션·부품·소모품의 수요확정부터 발주, 승인, FX-LIVE 입력, 선적, 통관, 입고, 검수, PO Match 및 지급까지의 업무를 단계형 웹 시스템으로 구현하기 위한 제품 요구사항을 정의한다.

현재 단계에서는 실제 업무 데이터를 받기 전이므로 샘플 데이터와 화면 직접 입력을 사용한다. 시스템은 로컬 컴퓨터에서 실행하며, 데이터는 브라우저 LocalStorage에 저장한다. 향후 Vercel에 웹 애플리케이션을 배포하고 Supabase Database/Storage/Auth로 저장·인증 구조를 확장할 수 있도록 계산·저장·화면 영역을 분리한다.

### 1.2 제품명

SCM 발주·입고관리 시스템

### 1.3 대상 사용자

초기 MVP는 단일 사용자 모드로 운영한다. 사용자는 영업, SCM/물류, 구매, 승인, 회계 업무를 하나의 화면에서 순차적으로 처리한다. 역할별 로그인과 권한은 이번 MVP에서 제외하지만, 업무 상태와 승인·FIX·입고·지급 이력은 기록한다.

### 1.4 제품 목표

- 수요와 재고를 기반으로 기기·옵션 발주량을 일관된 기준으로 계산한다.
- MOQ, Lead Time, Flexibility Rule, BOM, 장착율, Common품, 필수품을 계산에 반영한다.
- 발주계획의 보고·승인·FX-LIVE 입력·입고·지급 상태를 하나의 업무 Cycle에서 추적한다.
- 오류와 예외를 단계별로 표시하고, 필수 오류가 해결되기 전에는 다음 단계로 이동하지 못하게 한다.
- 실제 데이터와 Supabase 연계가 가능하도록 향후 확장 가능한 데이터 구조를 확보한다.

## 2. 범위

### 2.1 MVP 포함 범위

```text
0. OL 취합
→ 1. 수요 검증 및 수요 확정
→ 2. 전월 말 재고·Open PO 확인
→ 3. 기기 발주량 산출
→ 4. 옵션·부품·소모품 발주량 산출
→ 5. 발주금액 집계·사장 보고·승인
→ 6. FX-LIVE 입력 및 결과 검증
→ 7. 선적·통관·입고·검수·PO Match·지급
```

### 2.2 MVP 제외 범위

- 사용자 로그인, 역할별 권한, 다중 사용자 동시편집
- 실제 SFDC·ERP·WMS·FX-LIVE API 연계
- Excel/CSV 업로드 및 다운로드 자동화
- Supplier API와 자동 선적 데이터 연계
- 이메일·메신저 알림
- 실제 회계시스템 지급 실행
- 복잡한 수요예측 AI 모델

단, 제외 기능은 후속 개발을 고려하여 화면·데이터·서비스 경계를 분리한다.

## 3. 용어 및 업무 기준

| 용어 | 정의 |
|---|---|
| OL | 영업부서가 기종별 판매계획을 취합하여 물류에 공유하는 출고 Outlook. 제품과 부품을 포함한다. |
| 필요월도 | 기기·소모품·부품이 고객 출고를 위해 실제 필요한 월도 |
| Flexibility Rule | Supplier 제출 OL 대비 발주 수량 변경 허용범위. 전월 ±20%, 전전월 ±30%를 기본값으로 한다. |
| PRT | A3/A4 Printer 계열 제품군 |
| 장착율 | 기기 판매 시 특정 옵션이 함께 출하되는 비율 |
| Common품 | 여러 기종에 공통으로 사용하는 옵션·부품·소모품 |
| 옵션 필수품 | 특정 기기 또는 옵션 출하 시 반드시 포함되는 옵션·부품 |
| 평균 사용량 | 최근 3개월·6개월·12개월 기준의 기간별 평균 사용량 |
| MOQ | Supplier가 요구하는 최소 구매 수량 단위 |
| BOM | 기종별 구성 자재 명세 |
| SFDC | Salesforce 영업 파이프라인 |
| Open PO | 발주되었으나 아직 입고되지 않은 발주잔량 |
| FX-LIVE | 최종 발주량을 FIX하고 Supplier에 제출하는 시스템 |
| PO Match | PO, 입고수량, Invoice를 대조하여 지급 여부를 결정하는 업무 |

## 4. 제품 흐름

### 4.1 업무 Cycle

사용자는 기준월을 선택하여 업무 Cycle을 생성한다. 하나의 Cycle에는 수요, 재고, 산출, 승인, FX-LIVE, 입고 및 지급 데이터와 변경 이력이 연결된다.

### 4.2 단계 상태

```text
DRAFT
→ OL_REVIEW
→ DEMAND_CONFIRMED
→ INVENTORY_CHECKED
→ DEVICE_CALCULATED
→ OPTION_CALCULATED
→ APPROVAL_PENDING
→ APPROVED
→ FXLIVE_FIXED
→ INBOUND_TRACKING
→ RECEIVED
→ PO_MATCHED
→ COMPLETED
```

반려·재산출·재검토가 필요한 경우 다음 상태를 사용할 수 있다.

```text
REVIEW_REQUIRED, REJECTED, RECALC_REQUIRED, REAPPROVAL_REQUIRED, FIX_CHANGED
```

### 4.3 단계 이동 원칙

1. 사용자가 입력 또는 계산을 수행한다.
2. 시스템이 필수값, 형식, 참조값, 업무규칙을 검사한다.
3. 차단 오류가 없으면 다음 단계 버튼을 활성화한다.
4. 차단 오류가 있으면 오류 건수와 수정 대상 행을 표시한다.
5. 단계 완료 시 완료시각과 변경 이력을 저장한다.
6. 이전 단계의 핵심 데이터가 변경되면 영향받는 후속 단계에 재검토 상태를 부여한다.
7. 승인 후 발주량이 변경되면 재승인을 요구한다.

## 5. 기능 요구사항

### FR-001 업무 Cycle 생성 및 관리

- 기준월을 입력하여 새 Cycle을 생성할 수 있어야 한다.
- 기존 Cycle 목록을 조회하고 이어서 진행할 수 있어야 한다.
- Cycle별 현재 단계, 진행률, 마지막 저장시각, 상태를 표시해야 한다.
- 샘플 데이터로 새 Cycle을 시작할 수 있어야 한다.
- 샘플 데이터 초기화는 사용자의 확인 후 수행해야 한다.

### FR-002 단계 0: OL 취합

- 영업부서별 OL 행을 추가·수정·삭제할 수 있어야 한다.
- 필수 입력: 영업부서, 기종코드, 기종명, 상품구분, 필요월도, OL 수량.
- 기종·제품·부품·소모품을 구분할 수 있어야 한다.
- 수량은 0 이상이어야 하며 필요월도는 유효한 월 단위 날짜여야 한다.
- 중복·기종코드 누락·수량 오기입·비정상 증감을 경고해야 한다.
- OL 버전과 제출상태를 기록해야 한다.

### FR-003 단계 1: 수요 검증 및 확정

- SFDC 중요 Pipeline과 OL 외 Bulk Deal을 입력할 수 있어야 한다.
- 고객, 기종, 예상출고월도, 수량, 수주가능성, OL 반영여부, 사전재고 확보여부를 관리해야 한다.
- 과거 실적 Trend를 최근 3개월·6개월·12개월 기준으로 표시할 수 있는 구조를 제공해야 한다.
- 수급회의 결정사항과 Bulk Deal 재고 확보 여부를 기록해야 한다.
- 수요 유형을 확정·조건부·참고·제외로 구분해야 한다.
- 확정수요를 입력하고 수요 확정 상태로 전환할 수 있어야 한다.

### FR-004 단계 2: 재고 및 Open PO

- 전월 말 재고를 기종·품목·창고 기준으로 입력·조회할 수 있어야 한다.
- 예약/출고예정재고, 품질보류/수리중 재고를 구분해야 한다.
- Open PO 수량과 입고예정일을 입력해야 한다.
- 필요월도 전 입고 예정 Open PO만 적기 입고수량으로 반영해야 한다.
- 분할입고, 납기 지연, 입고 불확실성을 표시해야 한다.
- 가용재고를 자동 계산해야 한다.

### FR-005 단계 3: 기기 발주량 산출

- 기종·필요월도별 확정수요를 집계해야 한다.
- Supplier별 Lead Time, MOQ, 발주단위, 단가를 참조해야 한다.
- 기기별 기본 필요량과 MOQ 적용 후 발주량을 표시해야 한다.
- 전월 OL 대비 ±20%, 전전월 OL 대비 ±30%의 Flexibility Rule을 검증해야 한다.
- Rule 초과 여부와 사유 입력란을 제공해야 한다.
- 수동 조정수량과 조정사유를 기록해야 한다.
- 최종 제안량과 발주금액을 계산해야 한다.

### FR-006 단계 4: 옵션·부품·소모품 발주량 산출

- 기기별 BOM을 참조해야 한다.
- 필수품은 필수 여부를 기준으로 확보수량을 계산해야 한다.
- 선택 옵션은 장착율을 적용해야 한다.
- 평균 사용량 3개월·6개월·12개월 기준을 적용할 수 있어야 한다.
- Common품은 여러 기종의 소요량을 합산해야 한다.
- 옵션 전월 말 재고와 적기 입고 Open PO를 차감해야 한다.
- 옵션의 Lead Time, MOQ, 발주단위, Flexibility Rule을 반영해야 한다.
- 필수 옵션 부족, MOQ 초과발주, 납기위험을 표시해야 한다.

### FR-007 단계 5: 보고 및 승인

- 당월 총 발주금액을 기기·옵션·부품·소모품별로 집계해야 한다.
- 전월 및 작년 동월 발주금액과 비교할 수 있어야 한다.
- OL 제출량과 현재 제안량의 수량·금액 차이를 표시해야 한다.
- 차이사유를 수요증가, Bulk Deal, 재고부족, Open PO 지연, MOQ, 필수품, Lead Time 등으로 분류할 수 있어야 한다.
- 사장 보고자료 화면을 제공해야 한다.
- 승인·조건부 승인·반려·재산출 상태를 관리해야 한다.
- 승인일, 승인자, 승인 메모를 기록해야 한다.

### FR-008 단계 6: FX-LIVE 입력 및 검증

- 승인된 발주량을 FX-LIVE 입력용 데이터로 확인할 수 있어야 한다.
- PO번호, Supplier, 품목코드, 발주수량, 필요월도, 단가, 통화, 납기요청일, 발주금액, 승인번호를 검증해야 한다.
- FX-LIVE 입력 전·입력완료·FIX완료·오류 상태를 제공해야 한다.
- 산출량, 승인량, 입력량이 다르면 차이를 표시해야 한다.
- FIX 후 변경은 변경사유를 필수로 기록하고 재검토 상태로 전환해야 한다.

### FR-009 단계 7: 발주·선적·통관·입고·지급

- PO별 Supplier, 출발거점, 품목, 발주수량, 발주일을 관리해야 한다.
- 현지 선적일, 운송수단, 도착예정일, 도착지, 선적 지연사유를 관리해야 한다.
- 통관서류 확보상태, 통관상태, 창고입고예정일을 관리해야 한다.
- 실제 입고일, 입고수량, 검수결과, 파손·누락·불량을 기록해야 한다.
- Invoice번호와 Invoice금액을 기록해야 한다.
- PO Match 상태를 대기·일치·불일치·보류로 관리해야 한다.
- 지급상태를 대기·지급완료·지급보류로 관리해야 한다.
- 분할입고 시 미입고 잔량을 자동 표시해야 한다.

## 6. 계산 규칙

### 6.1 기기

```text
가용재고
= 전월 말 재고
- 예약/출고예정재고
- 보류재고
+ 필요월도 전 입고 예정 Open PO

기본 필요량
= MAX(0, 확정수요 - 가용재고)

최종 발주량
= 기본 필요량을 MOQ·발주단위 기준으로 올림 조정

발주금액
= 최종 발주량 × 구매단가
```

### 6.2 옵션·부품·소모품

```text
필수품 소요량
= 기기수요 × BOM 수량

선택품 소요량
= 기기수요 × BOM 수량 × 장착율

총 소요량
= 기기연동 소요량 + 평균 사용량 기반 수요

옵션 기본 필요량
= MAX(0, 총 소요량 - 옵션 가용재고)

옵션 최종 발주량
= 기본 필요량을 MOQ·발주단위 기준으로 올림 조정
```

초기 MVP에서는 옵션 수요 기준을 확정수요로 두며, 추후 운영정책에 따라 기기 발주량 기준으로 변경 가능하도록 계산 모듈의 입력을 분리한다.

### 6.3 Flexibility Rule

```text
전월 변경률 = (현재 발주량 - 전월 OL) / 전월 OL
전전월 변경률 = (현재 발주량 - 전전월 OL) / 전전월 OL
```

전월 OL 또는 전전월 OL이 0인 경우 Rule을 자동 판정하지 않고 확인 필요 상태로 표시한다. MOQ로 인한 초과는 초과 사유를 구분하여 표시한다.

## 7. 화면 및 UX 요구사항

### 7.1 공통 레이아웃

- 좌측에 0~7단계 네비게이션을 표시한다.
- 현재 단계, 완료 단계, 오류 단계, 재검토 단계를 색상과 아이콘으로 구분한다.
- 상단에 업무 Cycle 기준월, 상태, 마지막 저장시각을 표시한다.
- 화면 하단에 이전 단계, 저장, 다음 단계 버튼을 배치한다.
- 오류·경고 패널에서 오류 행으로 이동할 수 있어야 한다.
- 모든 입력 영역은 직접 추가·수정할 수 있어야 한다.

### 7.2 화면 목록

1. 업무 시작/ Cycle 목록
2. OL 취합
3. 수요 검증·확정
4. 재고·Open PO
5. 기기 발주량
6. 옵션·부품·소모품 발주량
7. 보고·승인
8. FX-LIVE 관리
9. 입고·지급
10. 업무 이력 및 설정

### 7.3 상태 표현

- 파란색: 입력 또는 진행 중
- 녹색: 완료·정상·일치
- 노란색: 경고·검토 필요
- 빨간색: 차단 오류·Rule 초과·불일치
- 회색: 미진행·참고

## 8. 데이터 모델

초기 LocalStorage 객체는 다음 구조를 사용한다.

```ts
type WorkflowCycle = {
  id: string;
  baseMonth: string;
  currentStage: number;
  status: string;
  createdAt: string;
  updatedAt: string;
  olRows: OlRow[];
  demandRows: DemandRow[];
  inventoryRows: InventoryRow[];
  supplierRules: SupplierRule[];
  bomRows: BomRow[];
  deviceRecommendations: DeviceRecommendation[];
  optionRecommendations: OptionRecommendation[];
  approval: ApprovalRecord;
  fxLive: FxLiveRecord;
  inboundRows: InboundRow[];
  auditLogs: AuditLog[];
};
```

각 배열의 상세 필드는 기존 Excel 운영양식의 `Input_OL`, `Input_SFDC`, `Input_Inventory`, `Master_BOM`, `Master_Rules`, `Inbound_PO` 컬럼을 기준으로 정의한다.

### 8.1 저장소 추상화

화면은 직접 LocalStorage를 호출하지 않는다. 다음과 같은 저장소 인터페이스를 통해 접근한다.

```ts
interface WorkflowRepository {
  listCycles(): Promise<WorkflowCycle[]>;
  getCycle(id: string): Promise<WorkflowCycle | null>;
  saveCycle(cycle: WorkflowCycle): Promise<void>;
  deleteCycle(id: string): Promise<void>;
}
```

MVP 구현체는 `LocalStorageWorkflowRepository`로 만들고, 추후 `SupabaseWorkflowRepository`로 교체한다.

## 10. 검증 및 예외처리

### 10.1 검증 수준

| 수준 | 처리 |
|---|---|
| 차단 오류 | 수정 전 다음 단계 이동 불가 |
| 경고 | 확인 후 저장 가능하나 보고·승인 시 표시 |
| 정보 | 참고용 표시 |

### 10.2 차단 오류 예시

- 확정수요가 없는 발주 대상
- 기종·품목코드 또는 필요월도 누락
- 음수 수량
- Supplier, 단가, MOQ, 발주단위 미등록
- BOM 또는 필수 옵션 기준정보 누락
- 발주량이 계산되지 않음
- PO Match에 필수 입력값이 없음

### 10.3 경고 예시

- Flexibility Rule 초과
- MOQ로 인한 과잉발주
- Open PO 납기 불확실
- Bulk Deal 수요 미확정
- 전월 또는 전전월 OL이 0인 품목
- Invoice·입고 수량 차이

## 11. LocalStorage 정책

- 저장 키는 `scm-workflow-cycles-v1`로 관리한다.
- Cycle 생성·입력·수정·계산·승인·FIX·입고상태 변경 시 자동 저장한다.
- 마지막 저장시각을 화면에 표시한다.
- 새로고침 후 동일 Cycle을 복원한다.
- 샘플 데이터 초기화 전 확인창을 표시한다.
- 저장 데이터가 브라우저별·기기별로 분리된다는 안내를 제공한다.
- 데이터 삭제, 브라우저 변경, 저장공간 초기화 시 데이터가 사라질 수 있음을 안내한다.
- JSON 백업/복원은 후속 기능으로 고려한다.

## 12. 비기능 요구사항

### NFR-001 실행환경

- Windows 로컬 환경에서 `npm install` 및 `npm run dev`로 실행 가능해야 한다.
- 기본 개발 포트는 `3000`으로 한다.
- 샘플 데이터가 설치 직후 표시되어야 한다.

### NFR-002 성능

- 샘플 데이터 기준 주요 화면 최초 표시 2초 이내를 목표로 한다.
- 입력 변경 후 계산 결과는 즉시 또는 300ms 이내 갱신한다.

### NFR-003 사용성

- 표 형태 데이터는 헤더 고정, 필터, 정렬을 지원한다.
- 숫자·금액·비율·날짜를 의미에 맞게 표시한다.
- 오류 메시지는 원인과 수정 대상 필드를 함께 표시한다.

### NFR-004 유지보수성

- 계산 로직은 UI 컴포넌트와 분리한다.
- LocalStorage 접근은 Repository를 통해서만 수행한다.
- 모든 핵심 타입을 TypeScript로 정의한다.
- 향후 Supabase 전환 시 화면 코드를 크게 변경하지 않도록 한다.

## 13. 테스트 및 완료 기준

### 13.1 테스트 범위

- 발주량, MOQ, Flexibility Rule, BOM, 장착율 단위 테스트
- 필수값·형식·참조 기준정보 검증 테스트
- 0단계부터 7단계까지 순차 진행 테스트
- 단계 완료 차단/허용 테스트
- 이전 단계 수정 후 후속 단계 재검토 테스트
- LocalStorage 저장·새로고침·복원 테스트
- 승인 후 변경 시 재승인 상태 테스트
- FIX 후 변경 이력 테스트
- 입고수량·Invoice·PO Match 불일치 테스트
- 주요 화면 반응형 및 오류 메시지 테스트

### 13.2 완료 기준

MVP는 다음을 모두 만족해야 한다.

1. 샘플 데이터로 전체 0~7단계를 순서대로 진행할 수 있다.
2. 차단 오류가 있으면 다음 단계로 이동할 수 없다.
3. 수량·기준정보 변경 시 기기·옵션 발주량과 금액이 재계산된다.
4. MOQ·Flexibility Rule·BOM·장착율·Lead Time이 계산에 반영된다.
5. 승인·FIX·입고·PO Match 상태와 이력이 저장된다.
6. 브라우저 새로고침 후 Cycle과 입력값이 유지된다.
7. 각 단계의 오류·경고·재검토 상태를 확인할 수 있다.
8. 로컬에서 별도 백엔드 없이 실행된다.
9. 저장소와 계산 모듈이 분리되어 Supabase 전환이 가능하다.
